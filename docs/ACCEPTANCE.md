# ACCEPTANCE.md — the parity policy

What the parity oracle is, what counts as passing, and how a divergence is
adjudicated. This is the policy the automated pipeline enforces; the moving
parts live elsewhere:

- **`docs/KNOWN_DEVIATIONS.md`** — the accepted deviation list (evidence per
  case). This doc says *how* a deviation earns its place; that doc *is* the list.
- **`docs/DATA_REFRESH.md`** — the monthly runbook and the gate mechanics
  (corpus / sweep / coverage / pytest / cargo).
- **`scripts/parity/normalize.py`** — the executable form of "what counts as
  passing" below.

---

## The oracle

- **Oracle** = the official `.plain` dump's `vpic.spvindecode`, run
  **unmodified** in a Postgres CI container over that month's dump. It is the
  sole source of truth. The Postgres port's dedup tiebreak already ends in
  `id ASC` — deterministic, no `NEWID()` — so no patch is needed to freeze it.
  The `ssrpw2` proc is never the oracle.
- **"Unmodified" is load-bearing.** Anything whose output becomes a committed
  baseline (`make check`, the frozen corpus, answer-key builds) runs against
  NHTSA's exact proc text. A mechanically-rewritten oracle whose equivalence is
  only *measured* — e.g. `ULTRAVIN_ORACLE_FAST_PROCS=1` (see
  `docs/ORACLE_TUNING.md`, `scripts/oracle.sh`) — is opt-in for bulk
  differential runs and off by default, precisely so the trust story stays
  "parity against NHTSA's text," not "against a transform of it."
- **Oracle collation** = `--lc-collate=C`, pinned in `docker-compose.yml`, and
  part of the contract. The tiebreak that governs *which* rows come back must
  match SQL Server; `C` does (verified over every key pair in the data) and a
  locale-aware collation does not. Do not run the oracle under a locale-aware
  collation, and do not compare answer keys built under different ones. The one
  field where `C` and NHTSA's SQL Server still disagree (element 144's charset
  order) is a documented deviation — see `docs/KNOWN_DEVIATIONS.md`.

## What counts as passing

- **Parity = field-for-field equality** of every resolved row — all 15
  `spvindecode` columns (`ElementId`/`Value`, sources, the space-delimited
  error codes/text, `SuggestedVIN`) — compared as multisets keyed by
  `ElementId`, **plus** the `GroupName`-rank ordering. `normalize.py`'s
  `diff_rows` is the canonical comparison; a case passes when it reports no
  field diff, no missing row, no extra row, and matching group-rank order.
- **Allowed nondeterminism — exactly one:** the **intra-group output row
  order**. `spvindecode`'s final `ORDER BY` is *only* the `GroupName` CASE (no
  secondary key), so rows within one group are emitted in Postgres-executor
  order — a non-spec, data-dependent artifact that varies per VIN. Parity checks
  the group-rank sequence and excludes the intra-group permutation. This is the
  "non-semantic intra-group row order" `scripts/oracle.sh` refers to.
- **Determinism:** same input dump bytes ⇒ byte-identical artifact ⇒ identical
  `blake3`. CI asserts two clean rebuilds from one dump match.

## How a divergence is adjudicated

**Default: fix the decoder.** Parity is the spec. Any divergence means the Rust
decoder is wrong and must be changed to match the unmodified oracle. Never
weaken a gate, and never hand-edit generated files (`vpic/**`,
`tests/parity_corpus.json`, manifest hashes) to make a diff disappear — those
are only ever regenerated by `vpic-import` and `scripts.parity.freeze`.

**Exception: a genuine upstream/oracle defect,** where the *oracle* is wrong and
ultravin is more correct. A deviation is accepted only when all of these hold:

1. **Reproducible evidence** that the defect is the oracle's, not ultravin's —
   the oracle contradicts its own sources, crashes on malformed data, or the
   dump contradicts the SQL Server database NHTSA actually publishes from. The
   evidence goes in `docs/KNOWN_DEVIATIONS.md`.
2. **Bounded scope.** The current invariant is that every accepted deviation is
   error/partial-VIN-only (elements 142/143/144/156/191); **clean full-VIN
   decode stays byte-identical to the oracle.** A divergence on a clean decode
   is a bug, not a deviation.
3. **Pinned and frozen.** The VIN is added to `KNOWN_DEVIATION_VINS`
   (`scripts/refresh.py`) — the machine-readable face of the deviation list —
   and frozen in the parity corpus, so the expected difference is locked and any
   *unexpected* change to it fails the gate.

The corpus gate accepts a diverging VIN **only** if it is already a documented
deviation; `freeze.py` will happily snapshot any current diff as the new
baseline, so this policy — not the freezer — is what stops a regression from
being laundered green.
