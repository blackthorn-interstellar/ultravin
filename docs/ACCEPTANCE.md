# ACCEPTANCE.md — the parity policy

What the parity oracle is, what counts as passing, and how a divergence is
adjudicated. This is the policy the automated pipeline enforces; the moving
parts live elsewhere:

- **`scripts/known_problems.json`** — the registry: one entry per VIN we
  deliberately do not match, with its kind, class, scope, upstream root cause,
  evidence pointer, and the documentation section that argues it. It is the
  single source of truth; `ORACLE_CRASH_VINS` / `KNOWN_DEVIATION_VINS` in
  `scripts/refresh.py` and `KNOWN_DEVIATIONS` in `scripts/parity/answerkey.py`
  are all derived from it.
- **`docs/KNOWN_DEVIATIONS.md`** — the evidence companion to that registry, one
  section per class. This doc says *how* an entry earns its place; the registry
  *is* the list and that doc is the proof.
- **`docs/DATA_REFRESH.md`** — the monthly runbook and the gate mechanics
  (corpus / sweep / known-problems / coverage / pytest / cargo).
- **`scripts/parity/normalize.py`** — the executable form of "what counts as
  passing" below.

---

## The oracle

- **Oracle** = the official `.plain` dump's `vpic.spvindecode`, run
  **unmodified** in a Postgres CI container over that month's dump. It is the
  sole source of truth. The Postgres port's dedup tiebreak already ends in
  `id ASC` — deterministic, no `NEWID()` — so no patch is needed to freeze it.
  The `ssrpw2` proc is never the oracle.
- **"Unmodified" is load-bearing.** Anything whose output becomes a committed
  baseline (`make check`, the frozen corpus, answer-key builds) runs against
  NHTSA's exact proc text. A mechanically-rewritten oracle whose equivalence is
  only *measured* — e.g. `ULTRAVIN_ORACLE_FAST_PROCS=1` (see
  `docs/ORACLE_TUNING.md`, `scripts/oracle.sh`) — is opt-in for bulk
  differential runs and off by default, precisely so the trust story stays
  "parity against NHTSA's text," not "against a transform of it."
- **Oracle collation** = `--lc-collate=C`, pinned in `docker-compose.yml`, and
  part of the contract. The tiebreak that governs *which* rows come back must
  match SQL Server; `C` does (verified over every key pair in the data) and a
  locale-aware collation does not. Do not run the oracle under a locale-aware
  collation, and do not compare answer keys built under different ones. The one
  field where `C` and NHTSA's SQL Server still disagree (element 144's charset
  order) is a documented deviation — see `docs/KNOWN_DEVIATIONS.md`.

## What counts as passing

- **Parity = field-for-field equality** of every resolved row — all 15
  `spvindecode` columns (`ElementId`/`Value`, sources, the space-delimited
  error codes/text, `SuggestedVIN`) — compared as multisets keyed by
  `ElementId`, **plus** the `GroupName`-rank ordering. `normalize.py`'s
  `diff_rows` is the canonical comparison; a case passes when it reports no
  field diff, no missing row, no extra row, and matching group-rank order.
- **Allowed nondeterminism — exactly one:** the **intra-group output row
  order**. `spvindecode`'s final `ORDER BY` is *only* the `GroupName` CASE (no
  secondary key), so rows within one group are emitted in Postgres-executor
  order — a non-spec, data-dependent artifact that varies per VIN. Parity checks
  the group-rank sequence and excludes the intra-group permutation. This is the
  "non-semantic intra-group row order" `scripts/oracle.sh` refers to.
- **Determinism:** same input dump bytes ⇒ byte-identical artifact ⇒ identical
  `blake3`. CI asserts two clean rebuilds from one dump match.

## How a divergence is adjudicated

**Default: fix the decoder.** Parity is the spec. Any divergence means the Rust
decoder is wrong and must be changed to match the unmodified oracle. Never
weaken a gate, and never hand-edit generated files (`vpic/**`,
`tests/parity_corpus.json`, manifest hashes) to make a diff disappear — those
are only ever regenerated by `vpic-import` and `scripts.parity.freeze`.

**Exception: a genuine upstream/oracle defect,** where the *oracle* is wrong and
ultravin is more correct. **ultravin intentionally does not reproduce documented
vPIC defects.** The parity invariant is therefore:

> ultravin's output is byte-identical to the oracle's for every VIN **except
> those registered in `scripts/known_problems.json`**.

That is the whole exception — there is no separate carve-out by output field.
Divergence on a **clean full-VIN decode is admissible**, on exactly the same
terms as any other entry. (Until 2026-08 the invariant was narrower: deviations
had to be error/partial-VIN-only, elements 142/143/144/156/191, and a clean
decode had to stay byte-identical. That bound is repealed. A defect that
corrupts a clean decode is not less of a defect for being more visible, and
reproducing it faithfully would mean shipping a wrong answer on purpose.) Each
entry still records its `scope` (`error-fields` / `clean-decode`) so the blast
radius is visible in the registry.

An entry is accepted only when all of these hold:

1. **Root-caused to a named upstream defect.** Not "the outputs differ" —
   *which* upstream artifact is defective, and how. A cache cell that
   contradicts the table it is derived from; a `pattern` row the oracle's own
   regex helper cannot compile while its sibling helper patches the same string;
   a dump that contradicts the SQL Server database NHTSA publishes from. If the
   root cause is unknown, the entry is not admissible **and the divergence is a
   bug in ultravin until proven otherwise.**
2. **Reproducible evidence**, stated in the registry's `evidence` field as a
   one-line pointer to the defective artifact, and argued in full in the
   `docs/KNOWN_DEVIATIONS.md` section the entry's `doc` anchor names. **An
   output diff never qualifies** — it is the observation being explained, not
   the explanation.
3. **Registered and frozen.** The VIN goes in `scripts/known_problems.json`
   (every field populated) and, where the oracle answers at all, into the parity
   corpus, so the expected difference is locked. Both halves are mechanical:
   `refresh.corpus_vins_file` unions every registered `deviation` into the VIN
   list the monthly re-freeze asks for, and `refresh.deviation_shape_changes`
   compares each one's re-frozen `expected_diff` against the shape committed at
   `HEAD` — a difference fails the **known-problems** gate naming the VIN. Only
   VINs registered as deviations in *both* HEAD's registry and the current one
   are compared: a registration added this cycle is establishing its shape, and
   a retired entry is no longer held still. HEAD moves when the refresh merges,
   so a deliberate change fires the gate once and then becomes the baseline.
4. **Re-verified every refresh.** `scripts/parity/known_problems.py` re-probes
   every registered VIN against each new dump and the **known-problems** gate
   fails the run when one heals or cannot be verified. An entry that stopped
   reproducing is retired, not kept: a stale excuse silently forgives the next
   real regression on that VIN.

Everything else is still a bug. **Output that differs from the oracle without a
root-caused upstream defect behind it is a defect in ultravin and gets fixed in
the decoder** — never registered, never excused. The corpus gate accepts a
diverging VIN **only** if it is already registered; `freeze.py` will happily
snapshot any current diff as the new baseline, so this policy — not the freezer —
is what stops a regression from being laundered green.
